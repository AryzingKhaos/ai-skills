# work-time

自动统计 Aaron **用 AI 工作的真实时长**（主要是 plan B / 编程 / build skill 的投入）。数据来自本机对话记录，无需手动打卡。

## 定位（硬约束：观测，不考核）

- **只报事实**：投了多久、分成几个连续段、分布在哪几天。
- **绝不做的事**：❌ 不设"每日/每周目标时长" ❌ 不评判"够不够勤奋" ❌ 不出"未达标"警告 ❌ 不与 dota 时长做"该多工作少玩"的对比说教。
- **为什么**：plan B 是创造性工作，价值在产出不在工时。用工时 KPI 考核它 = 复制 Aaron 痛恨的 N 的管理方式，会破坏刚重建的心流、触发"高自评严苛→我不够"的自责。**这是一块仪表，不是一根鞭子。**
- 与 dota-playtime 的关键差异：dota 有上限（防沉迷）；work-time **不设下限**（逼产出会毁产出）。

## 原理

Claude + Codex 的每条记录都带 `timestamp`。脚本：收集全部 → 按时间排序 → 相邻间隔 ≤`gap-min`(默认30)分钟视为同一连续工作段 → 每段开始前加 `prep-min`(默认5)分钟准备、结束后加 `read-min`(默认10)分钟阅读 → 求和。

> 说明：只统计"用 AI 的工作"。**看书/纯手写等不经过 AI 的工作不会被记到**——这是已知盲区。**这个盲区由下面的「手动打卡」填补。**

## 手动打卡（start / end / endTime）——填补自动的盲区

用于记录**自动推算抓不到的工作**（看书、开会、线下写代码、纯思考）。与自动段**互补、不重叠**，存**单独的「手动打卡明细」表**，**精确起止、不加准备/阅读补偿**。脚本 `scripts/manual_clock.py`，进行中状态存 `scripts/.manual_clock_state.json`。

```bash
python3 scripts/manual_clock.py start "本次大致工作内容"   # 标记开始（内容可选）
python3 scripts/manual_clock.py end   ["可选内容"]         # 现在结束；若带内容则覆盖 start 的内容
python3 scripts/manual_clock.py endTime "22:30"           # 忘记 end 时补结束时间；也可 "MM-DD HH:MM"
python3 scripts/manual_clock.py status                    # 看当前有没有进行中的打卡
```

规则（均已内置，照实转达即可）：
- **start**：记录当前时间 + 内容。若**已有一段未结束**（忘了 end）→ **提示用户先 end/endTime 结束它，不擅自处理**（用户选定）。
- **end**：用当前时间结束。**若 end 带了内容，覆盖 start 的内容**（用户规则）；不带则沿用 start 的内容。
- **endTime**：备用，给具体结束时间（`HH:MM` 默认同日；结束早于开始自动判为跨天次日；也支持 `MM-DD HH:MM`）。
- 结束时**直接写入台账的「手动打卡明细」表并清空状态**，无需再跑归档。
- 「内容」列 = 干了什么；「备注」列留空给用户手填产出/心流。
- **不加补偿时间**（自动段加 5+10 是因为对话记录不含准备/阅读；手动是精确起止，不需要）。

## 执行

```bash
# 当前自然周（本周一 00:00 → 现在）
python3 scripts/work_time.py
# 过去 N 天（截止昨天 24:00）
python3 scripts/work_time.py --days 7
# 调参（间隔/准备/阅读分钟）
python3 scripts/work_time.py --gap-min 30 --prep-min 5 --read-min 10
```

脚本输出：真实时长、按天表、工作段明细，末尾一段 `SIGNALS:` JSON（total_seconds / segments / days_worked 等）。

## 讲给用户

- 报**时长 + 段数 + 覆盖天数**，中性陈述。若有历史归档，说一句"较上次趋势"（看趋势，不评判绝对值）。
- **可以说**的观察：段的分布（是集中还是零散）、和心流的关系（"上午那段 1.5 小时是连续的，可能是心流"）——这类**描述性**洞察有用。
- **不可以说**的：任何"你该多做点/做得不够/要加油"的规劝。用户想聊状态时按普通对话，但 skill 本身只观测。
- 提一句盲区：看书/离线工作没被算进来。

## 归档（每次跑完都做，是默认行为，两级表）

台账文件：`/Users/aaron/workspace/个人/生活/工作时长.md`。**无论自然周模式还是 `--days N` 模式，跑完都归档**（归档是跑 skill 的默认行为）。因为归档是按"段的真实日期"upsert 的，与查询窗口无关，所以两种模式都能正确写入、不会错位。文件里维护**两个表**：

### 表一「工作段明细（全部）」（每个连续工作段一条，含本职工作）
表头（文件为空时建）：`| 日期 | 起 | 止 | 时长 | 项目 | 备注(产出/状态) |`
- 数据来自 `SIGNALS.seg_details`（每个 seg 一行）：`date（带周几）/ start / end / human / project`。
- **upsert 键 = 「日期+起」**：已有该段 → 更新时长/项目/止；**「备注」列不覆盖**。没有 → 追加。
- 按 日期+起 升序。「项目」列 = 该段涉及的项目末段名，多个用 `/` 分隔（按事件数从多到少）。
- **「备注」列留给用户手填**产出/心流——明细表的灵魂，工时和项目只是背景。

### 表二「planB 工作段明细」（排除本职工作项目 pro 后重新切段）
表头：`| 日期 | 起 | 止 | 时长 | 项目 | 备注(产出/状态) |`
- 数据来自 `SIGNALS.planb_seg_details`（已排除 `work_projects`，默认 pro）。upsert 规则同表一（键=日期+起，备注不覆盖）。
- 注意：排除本职项目后，原本混着 pro 的大段会被切开，所以 planB 段数可能比全部**还多**、时长更短——这是正确的。
- 这是**观测 planB 真实投入**的表（排除了上班时间），比表一更贴"我给 plan B 投了多少"。

### 表三「周汇总」（按自然周聚合）
表头：`| 自然周（周一~周日） | 全部时长 | 全部段数 | planB时长 | planB段数 | 工作天数 | 更新时间 |`
- 「planB时长/段数」用 `planb_total_human`/`planb_segments`（该周从 planB 明细筛出重算）。
- **按"段的真实日期"归周，不按查询窗口**：把本次 `seg_details` 里每一段，按其 `date` 落到所属自然周（周一~周日），分周聚合。**关键**：`--days N` 窗口可能横跨两个自然周，所以要拆开分别归——绝不能把整个窗口当成一周。
- 每个受影响的自然周做 upsert（按自然周区间键 `YYYY-MM-DD ~ YYYY-MM-DD`）：
  - **只用本次扫到、且属于该周的段**重算该周的「时长/段数/工作天数」，与已有行取并集更新（若某周此前已有记录，用"该周所有已知段"的合计——即读旧明细表按周重算，保证不因单次窗口只覆盖半周而把数字改小）。**稳妥做法：周汇总的数字 = 从明细表里筛出该周所有段，现算现填**，而不是直接用 SIGNALS 的窗口合计。
  - 「更新时间」用 currentDate。
- 纯自动统计，无备注列（个性化的东西都在明细表的备注里）。

写完在回复里带一句"已记录到 工作时长.md（明细 N 段 + 周汇总）"。

## 注意

- 只读对话记录（不修改）；台账只在自然周模式追加/更新。
- 明细表的历史行只在"同一段"再次被扫到时更新时长，**已手填的备注永不覆盖**。
- 记录的是"投了多久 + 在哪个项目 + 做了什么产出"，**不是**"够不够"——台账里永远不出现目标值/达标判断。
