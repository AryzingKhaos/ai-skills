# work-time

统计 Aaron 使用 Claude Code + Codex 工作的真实时长，并按完整工作目录路径划分为：

- `工作项目`
- `planB项目`
- `其他项目`（未命中前两类路径的全部记录）

这是一块观测仪表，不是考核工具：只报告投入时长、连续段和日期分布，不设目标，不判断够不够勤奋。

## 权威文件

- 项目目录与汇总台账：`/Users/aaron/workspace/个人/生活/工作时长.md`
- 规范化原始事件库目录：`/Users/aaron/workspace/个人/生活/工作时长-originData`
- 自动统计脚本：`scripts/work_time.py`
- 手动打卡脚本：`scripts/manual_clock.py`

## 自动统计口径

1. Claude 数据来自 `~/.claude/projects/**/*.jsonl`，并同时发现每个 `~/.claude.*` 目录下的 `projects/**/*.jsonl`。
2. Codex 数据来自 `~/.codex/sessions/**/*.jsonl`。每次运行会检查全部 JSONL 的文件元数据，但有有效游标时只读取新文件、追加尾部或发生替换/截断的文件，不再解析所有历史正文。
3. 先按「originData 增量归档（强制步骤）」完成归档，再计算并更新台账；只保存事件ID、时间戳、来源、完整项目路径、记录类型，不保存对话正文。
4. 备份目录中的相同记录按事件ID去重。实际计时时，再按“时间戳 + 来源 + 完整项目路径”去重，避免重复快照影响项目权重。
5. 从台账的「项目目录」分组列表读取路径。路径支持 `*`，并自动包含匹配目录的子目录。
6. 匹配优先级是 `工作项目 → planB项目 → 其他项目`；未命中前两类的一律归为其他项目。
7. **先分类**：逐条事件按完整项目路径确定为 `工作项目`、`planB项目` 或 `其他项目`。
8. **再分别切段**：把三类事件分开，各自在本分类内部按时间排序；只有同类相邻事件间隔不超过 30 分钟才合并为一个连续段。
9. 不同分类互不连接、也不再选“主导分类”。例如工作事件之间相隔 40 分钟，即使中间有一条 Plan B 事件，两个工作事件仍是两段；Plan B 事件另算自己的段。
10. 每个分类段独立在开始前加 5 分钟准备、结束后加 5 分钟阅读。默认参数：`gap-min=30`、`prep-min=5`、`read-min=5`。完整路径用于分类与 originData；明细表只展示末级文件夹名。

这种“先分类、再分别计时”的顺序确保工作项目和 Plan B 各自反映真实活动，不会因为两类事件交错而让其中一类吞掉另一类。由于各分类独立切段并各自获得准备/阅读补偿，它们的墙钟区间可以重叠，周汇总里的「分类合计」是三类时长的算术和，不是去重后的墙钟并集。

## 项目路径配置

路径只在 `工作时长.md` 的「项目目录」分组列表里维护，不在脚本中硬编码。脚本读取但不改写已有的项目目录排版：

```markdown
## 项目目录
### 工作项目
- `/Users/aaron/code/tron*`

### planB 项目
- `/Users/aaron/workspace/llmWikis`
```

未命中以上两组路径的记录自动归为「其他项目」，不需要在项目目录中逐项维护。

新增、删除或修改工作/planB 路径后，用 originData 直接重分已有台账，不重新扫描 Claude/Codex 原日志：

```bash
python3 scripts/work_time.py --from-origin --reclassify-ledger
```

备注优先按「分类+日期+起」保留；旧版未分类表只有在同一开始时间唯一对应一个新段时才迁移。若重新分类后无法安全匹配，脚本会停止写入并报告冲突，避免静默丢备注或把备注复制到重叠分类。

## originData 增量归档（强制步骤）

每次正常执行自动统计时，必须先归档原始事件，再计算时长和更新台账。严格按以下顺序执行：

1. 对 originData 目录加进程锁，读取目录下全部 `.md`，按事件ID合并；保留所有历史事件，也兼容迁移进来的 legacy 汇总文件。
2. 校验 `.scan-state-v1.json` 中的归档事件数和指纹。游标缺失、损坏、版本不符或归档内容被删改时，安全地完整扫描一次并重建；正常情况进入增量模式。
3. 发现 `~/.claude`、全部 `~/.claude.*` 和 Codex 下的所有 JSONL，但先看设备号、inode、字节数、纳秒级 mtime/ctime 及游标前的头部/尾部锚点：
   - 完全未变化：不读取内容；
   - 原文件追加：从已提交字节偏移继续读；
   - 新文件、替换、截断、等长改写或锚点不一致：只对该文件从头重扫；
   - 末尾 JSON 尚未写完：游标停在该行起点，下次补齐后再收录；
   - 文件扫描中被替换：已读事件可以去重归档，新 inode 从 0 留待下次读取。
4. 只挑出事件库里还没有的事件，按事件的本地时区归入周一至周日的自然周；每周原子写一个 Markdown，例如 `2026-W34_2026-08-17--2026-08-23.md`。迟到事件会更新其实际发生周，而不是当前周。
5. 所有受影响周文件写成功后，才原子更新 `.scan-state-v1.json`。进程中断时最多在下次重复读取并按事件ID去重，绝不能先推进游标再漏掉归档。
6. 从合并后的完整事件库计算分类时间段，最后更新 `工作时长.md`。日期窗口只限制本次时长计算，不限制增量归档。

首次迁移或游标需要重建时会有一次完整扫描；建好游标后，正常运行只读变化文件。目录中的 `.scan.lock` 用于阻止两个统计进程互相覆盖。

旧单文件归档保留为：

```text
工作时长-originData/legacy_2026-03-21--2026-08-21.md
```

它继续作为历史事件库参与去重和复算；后续新增事件只写入自然周文件，不把旧汇总重复拆写一遍。

只有显式使用 `--from-origin` 时，才跳过源日志扫描和 originData 写入，直接复用已有归档。`--days`、`--start/--end` 只限制统计窗口，不得跳过 originData 归档；单独使用 `--no-archive` 只是不写工作时长台账，仍要刷新 originData。

只有归档/游标异常恢复时才使用 `--rebuild-scan-state`，它会故意完整扫描一次。它不能与 `--from-origin` 同时使用。

每个 originData Markdown 的事件行字段为：

```markdown
| 事件ID | 时间戳（ISO 8601，本地时区） | 来源 | 项目路径 | 记录类型 |
```

- 保留完整路径，确保项目分类变化后可直接复算。
- 不保存消息、提示词、回答等对话正文。

## 执行

```bash
# 当前自然周：刷新 originData、统计、归档
python3 scripts/work_time.py

# 过去 N 个完整日（截止昨天 24:00）
python3 scripts/work_time.py --days 7

# 指定日期范围；end 是不包含的结束日期
python3 scripts/work_time.py --start 2026-08-03 --end 2026-08-10

# 项目路径变化后，直接复用 originData 重分台账现有日期范围
python3 scripts/work_time.py --from-origin --reclassify-ledger

# 只复用 originData，不写台账
python3 scripts/work_time.py --from-origin --no-archive

# 仅在游标故障恢复时：完整扫描一次并重建增量游标
python3 scripts/work_time.py --rebuild-scan-state

# 显式调参
python3 scripts/work_time.py --gap-min 30 --prep-min 5 --read-min 5
```

脚本默认完成三件有顺序保证的写操作：

1. upsert 有新增事件的自然周 originData Markdown；
2. 更新 `.scan-state-v1.json` 增量游标；
3. 用本次窗口重新生成三类时间段，并重算 `工作时长.md` 周汇总。

末尾输出 `SIGNALS:` JSON，包含窗口、分类路径、origin 总/新增事件数、增量模式、发现/读取/跳过文件数、读取字节数、更新的周文件以及三类时长/段数/明细。

## 台账结构

自动统计维护四个表：

### 工作项目时间段

只含路径匹配「工作项目」的记录。

### planB项目时间段

只含路径匹配「planB项目」的记录。

### 其他项目时间段

只含未命中工作和 planB 路径的记录。看到这里有应归类的项目时，应先更新「项目目录」，再执行 `--from-origin --reclassify-ledger`。

三张明细表统一使用：

```markdown
| 日期 | 起 | 止 | 时长 | 项目 | 备注(产出/状态) |
```

- 自动更新窗口内的行，窗口外历史不动。
- 同一分类段涉及多个项目时，只显示去重后的末级文件夹名，并用中文顿号「、」分隔。
- 「备注」按 `分类+日期+起` 保留；它用于手填产出或心流状态。同一时间出现多个分类段时，备注不会串到另一类。

### 周汇总

按自然周列出三类时长、各自段数、分类合计、活跃天数和更新时间。周汇总从三张自动分类明细表与手动打卡明细共同重算；完成的手动段计入 planB项目时长与段数。「分类合计」直接相加三类独立计时结果，分类区间有重叠时不会做跨分类去重。

## 手动打卡：填补自动盲区

自动统计抓不到看书、开会、线下写代码、纯思考。使用：

```bash
python3 scripts/manual_clock.py start "本次大致工作内容"
python3 scripts/manual_clock.py end "可选：覆盖 start 的内容"
python3 scripts/manual_clock.py endTime "22:30"
python3 scripts/manual_clock.py status
```

- `start` 是显式的 planB 归类；只有随后用 `end` 或 `endTime` 完成的时段才进入统计，进行中的打卡不预估时长。
- 完成的手动段按精确起止计入 planB项目，不加准备/阅读补偿，并立即刷新周汇总。
- 已有未结束打卡时，不擅自覆盖；提示先 `end` 或 `endTime`。
- 手动段原始记录仍写入独立的「手动打卡明细」表，与自动段不重叠；planB项目时间段表不重复抄写该行。

## 回复用户

- 分别报告工作项目、planB项目、其他项目的时长、段数和覆盖天数。
- 可以描述集中/零散、最长连续段、日期分布等事实。
- 提醒看书和离线工作等不会自动计入。
- 不设目标、不做达标判断、不用工时评价努力程度，也不与游戏时长做说教式对比。
- 完成归档后说明：本次是 bootstrap/rebuild 还是 incremental、发现/实际读取/跳过多少日志文件、originData 新增/总事件数、更新了哪些自然周文件，以及台账更新了哪些日期或周。
