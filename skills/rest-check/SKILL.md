# rest-check · 请假触发判定

机制设计出处：`/Users/aaron/workspace/个人/人生规划/人生游戏/休息机制.md`
**那份文档是设计，本 skill 是它的执行者。规则要改，先改文档再改脚本。**

## 这个 skill 存在的理由

Aaron 独居后没有共同决策人，核心矛盾是：**自己给自己的许可没有约束力，说出口的同一秒就能撤销。**
所以休息不能设计成许可，必须设计成义务——一个既定额度，人只负责执行，不负责判断该不该。

机制文档第五节把这件事说死了：

> 若流程是「我去看数据、判断自己超没超」→ 会出现「再看看」「这周特殊」→ **主观口子一开，整套机制作废。**
> 必须是：跑脚本 → 直接输出「今天该请假 / 不该」。人不参与判定，只执行结果。
> 这才是需要的那个客体：**一个不听辩解的程序。**

**你（Claude）是这个程序的传声筒，不是它的复审人。**

## 执行流程

### 1. 先确认数据新鲜

脚本会检查两个台账的「更新时间」，超过 2 天没刷新会打印警告。
**看到警告就先刷新再判定**，顺序是：

```bash
# 工作时长台账陈旧
/work-time
# DOTA2 台账陈旧
/dota2-playtime
```

刷新数据是允许的，因为它改的是**读数的准确性**；重新解读读数不允许，因为它改的是**判定**。

### 2. 跑判定

```bash
python3 <skill目录>/scripts/rest_check.py
```

输出直接给出结论（🛑 该请假 / ✅ 不该 / 🧊 冷却期内 / ⛔ 配额已用尽）、命中了哪几条规则、
全部读数、本季度配额消耗。**把脚本输出原样转达给用户**，可以补充格式，不要补充判断。

### 3. 结论是 🛑 该请假时

告诉用户：提交年假，然后记录支取。**不要问「你要不要考虑一下」**，那正是这套机制要绕开的东西。

```bash
python3 <skill目录>/scripts/rest_check.py --take 2026-09-05 --rule 4 --note "可选备注"
```

`--take` 记的是**实际休的那一天**，不一定是跑判定的当天。

## 四条触发规则（OR 逻辑，任一满足即触发）

| # | 条件 | 抓什么 | 数据来源 |
|---|---|---|---|
| 1 | 连续 2 个完整周「工作项目」≥ 基线 × 1.25 | 持续超载 | 工作时长.md 周汇总表 |
| 2 | 连续 21 天没有一整天完全不工作 | 无恢复窗口 | 工作时长.md 三张明细表 |
| 3 | 工作项目 ≥ 阈值 **且** 同周 DOTA 超限 | **麻醉信号** | 两个台账 |
| 4 | 季度过半、配额一天没用 → 强制支取 | 执行「配额是下限」 | 休息台账.md + 日历 |

- **第 3 条是 AND 不是 OR**：DOTA↑ + 工时↑ = 麻醉；DOTA↑ + 工时正常 = 只是在玩，中性甚至是好事。
- 第 3 条**复用 DOTA2 台账既有的「是否超限」列**，不新造阈值。`💰 动用结余（合法）` 算未超——花结余是已批准额度的提取。
- 第 4 条不依赖任何时长数据，只看日历和配额消耗，**所以它永远可用**。

### 判定口径（已定，不要临场改）

- **「完整周」**：结束日早于今天的自然周。当周还没过完，不参与任何判定。
- **第 2 条的「完全不工作」**：当天在「工作项目时间段」「planB项目时间段」「手动打卡明细」三张表里
  **都没有记录**才算休息日。**「其他项目」不算工作**（已确认的口径）。
  连续天数从**昨天**往回数，今天不算（今天还没过完）。
- **配额**：请假日每季度**至少 1 天、最多 2 天**（自然季度）。
- **冷却期 14 天**：距上次支取不足 14 天，即使命中规则也不触发，输出 🧊。
  防止连续支取烧光配额。
- **配额用尽**：本季度已支取 2 天时命中规则 → 输出 ⛔，改排降载日，不再请假。

### 基线（只降不升）

- 阈值 = 工作项目基线 × 1.25，基线变则阈值跟着变。
- 每次判定用最近 **12 个完整周**的工作项目时长**中位数**重算（不足 12 周就用现有的）。
- ⭐ **算出来更低就下调，更高就不采纳。** 适应了更高的工作量不是基线该涨，那是慢性透支。
- 当前基线 `17h43m` → 阈值 `22h09m`（机制文档写的 22h 是这个数的整数近似）。

## ⛔ 你（Claude）在这个 skill 里不许做的事

这一节比上面所有内容都重要。违反其中任何一条，这套机制就等于没有。

1. **不许重新解读读数。** 脚本说 23h46m ≥ 22h09m，那就是超了。不要说「但那周有个特殊项目」。
2. **不许接受申辩。** 用户说「这周不算」「我再看看」「等这个需求上线」——
   原样重复脚本结论，然后闭嘴。你不是来协商的。
3. **不许把结论软化成建议。** 不要写「建议你考虑休息一下」。脚本说该请假，就是**该请假**。
4. **不许自己改阈值、改口径、改配额**来让结论变得更「合理」。规则改动只能由 Aaron 改机制文档。
5. **不许替用户跳过 `--take` 记录。** 没记录 = 冷却期和配额判不了 = 第 4 条会误触发。
6. **不许因为结论是 ✅ 不该请假就少说话。** 读数照样完整给出——它是下次判定的上下文。
7. **不许劝用户多休息或少休息。** 配额有下限也有上限，两头都由脚本管。

允许你做的只有三件：**刷新数据源、转达脚本结论、按用户指令记录支取。**

## 首次使用要做的一件事

台账是新建的，**里面没有历史支取记录**。如果本季度已经休过假，先补录，否则第 4 条会立刻误触发：

```bash
python3 <skill目录>/scripts/rest_check.py --take 2026-07-18 --rule 手动 --note "补录"
```

补录完再跑一次判定。

## 数据坑（脚本已处理，改代码时别踩回去）

- ⚠️ `DOTA2时长.md` 从 2026-08-17 起，时长格式由 `17h52m` 变成 `17 小时 52 分钟`。
  **只匹配 `\d+h\d+m` 的正则会静默丢行且不报错。** 两种格式都必须兼容。
- ⚠️ 工作时长台账**只统计「经过 AI 的工时」**——会议、沟通、code review、看文档都不计入。
  所以**绝对阈值（如「9 小时/天」）不适用，只能用相对偏离**，这也是阈值挂在基线上的原因。
- ⚠️ `手动打卡明细` 里的日期**不一定**出现在 `planB项目时间段` 表里（例：2026-08-23）。
  第 2 条必须取三张表日期的并集，漏掉手动打卡会把工作日误判成休息日。
- ⚠️ 周汇总表含**当周未完成**的行。判定只用结束日早于今天的完整周。
