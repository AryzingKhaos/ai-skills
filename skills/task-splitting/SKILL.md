# Task Splitting 任务拆分与工时评估

把一份需求文档（PRD）拆成**可执行、可估时、每项不超过 4h** 的细分任务，并基于**运行目录下的真实代码**评估工作量，产出可直接粘贴进 Excel 的工时表。

## 输入

- **需求文档（必填）**：一份 markdown PRD，路径形如 `docs/link-ai-prompt/roleflow/requirements/<版本>/raw/prd-xx.md`。里面通常含：关联模块（M01…）、需求项（N-01…）、业务规则（BR）、变更矩阵、i18n 文案表、埋点表、验收表等。
- **代码目录（默认 = 当前运行目录）**：拆分时**必须读取运行目录下的真实代码**来评估每项工作的真实大小，而不是只看 PRD 字面描述。

## 输出（4 列，可直接粘贴进 Excel）

| 列 | 含义 | 约束 |
|---|---|---|
| **任务大类** | 工作的归类（按模块 / 按层 / 按需求项分组） | 同一大类多行重复填写大类名即可 |
| **任务具体名称** | 一个可独立交付的细分任务 | **每项的『无AI估时』不得超过 4h**，超了必须继续拆 |
| **大致估时（无AI · 人时）** | 资深工程师纯手写、不借助 AI 的人时 | 数字，单位小时；这是判定 4h 上限的基准 |
| **大致估时（有AI · 人时）** | 同一工程师借助 AI（Claude Code 等）的人时 | 数字，单位小时；通常 ≤ 无AI 估时 |

格式硬要求：**用制表符（Tab）分隔的纯文本（TSV）**，放进代码块输出。TSV 粘进 Excel 会自动分列；markdown 表格粘进 Excel 不会分列，**不要**用 markdown 表格当最终交付物。

## 启动前必须确认

如果用户没在提示里说清，**先确认下面几项再开工**：

1. **PRD 文件路径**（必填，没有就让用户给）。
2. **代码目录**：默认就是当前运行目录；若需求只涉及某个子目录 / 子包，确认范围以便聚焦评估。
3. **拆分粒度的归类口径**：按「模块（M01…）」还是按「实现层（数据 / UI / 交互 / 联调 / 测试…）」分组任务大类（默认按模块，子任务内再体现层次）。
4. **是否同时存成文件**：默认只在对话里输出 TSV 代码块；需要的话再存成 `.tsv` / `.csv`（确认存放路径）。

## 工作流

### Step 1 · 通读需求文档

用 `Read` 读完整份 PRD，理清：

- **涉及哪些模块 / 需求项**（如 M01…M12、N-01…N-14），各自改动量级（普通改动 vs ⚠️ 基线级改动）。
- **每个需求项要做什么**：UI 表现、交互逻辑、业务规则（BR）、异常分支（E）、验收（AC）。
- **横切工作**：i18n 文案表、埋点表、跨模块影响、安全 / 拦截策略、数据模型变更。
- **非目标（Out of Scope）**：明确不做的部分，**不要**为它们估时。

> PRD 里的「需求项 / 模块」是天然的拆分起点，但**不是**最终颗粒度——一个需求项往往要再拆成数据、UI、交互、自测等多条 ≤4h 的子任务。

### Step 2 · 勘察运行目录代码

**这一步决定估时是否靠谱，不能跳过、不能凭空猜。** 用 `Explore` / `Grep` / `Glob` / `Read`：

- 把 PRD 的模块名（如「账户管理」「DApp 连接」）映射到**真实代码路径 / 组件 / 文件**。
- 评估每处改动的真实复杂度：是新增页面、改造已有组件、动数据模型、还是动底层 Provider / 路由拦截。
- 找**可复用的现成实现**（已有相似组件 / 工具函数 / 枚举）——能复用的任务估时要相应下调。
- 识别**高风险 / 高耦合点**：基线级模块、跨模块共享状态、底层拦截、安全边界——这些估时要上调，且更难被 AI 提效。

派 `Explore` agent 做广度搜索，自己只接收结论，避免被大量文件淹没。

### Step 3 · 拆分任务（每项 ≤ 4h）

把工作拆成细分任务，并归到任务大类。一份功能型 PRD 通常覆盖这些工作类型（按需取舍，别漏）：

- 需求理解与技术方案设计
- 数据模型 / 账户类型 / 枚举等底层结构
- UI / 页面 / 组件开发（含状态还原）
- 交互逻辑 / 状态管理 / 路由
- 跨模块改造与影响处理
- 底层 / Provider / 拦截 / 安全防护
- i18n 文案接入
- 埋点接入
- 自测 / 联调
- QA 测试用例编写与执行
- 回归与发布前检查

**4h 上限规则**：以**无AI估时**为准，任何一条 > 4h 必须继续拆，直到每条都 ≤ 4h。拆分要保证每条「可独立交付、可单独验收」，不要为了凑 4h 硬切成无意义的碎块。

### Step 4 · 双轨估时（无AI / 有AI）

对每条子任务给两个人时：**资深工程师纯手写**（无AI）与**同一人借助 AI**（有AI）。

AI 提效不是一刀切打折，按任务性质分档（系数 = 有AI ÷ 无AI）：

| 任务性质 | 例子 | AI 提效 | 有AI ≈ 无AI × |
|---|---|---|---|
| 模板 / CRUD / UI 还原 / i18n / 埋点接入 | 静态页面、文案接入、列表渲染 | 高 | **0.3 – 0.4** |
| 常规业务逻辑 / 状态 / 组件改造 | 表单校验、状态切换、已有组件加字段 | 中 | **0.4 – 0.6** |
| 复杂业务规则 / 跨模块 / Provider 拦截 / 架构 / 安全边界 | 底层拦截、多链识别、基线级改动 | 低 | **0.6 – 0.8** |
| 联调 / 真机测试 / 评审沟通 / 需求确认 | 跨端联调、走查、开会对齐 | 几乎不提效 | **0.8 – 1.0** |

估时是**大致量级**，不是精确承诺。带上关键假设（如「复用现有 XX 组件」「未含 Figma 出稿时间」）。

### Step 5 · 输出 Excel 可粘贴表格

输出一个 **TSV 代码块**（Tab 分隔），含表头行、所有任务行、以及一行合计：

```
任务大类	任务具体名称	大致估时(无AI·人时)	大致估时(有AI·人时)
账户数据模型	扩展账户类型枚举新增「观察钱包」类型	3	1
账户数据模型	观察钱包地址 4 链识别与本地存储结构	4	2
导入流程(N-01/N-02)	钱包管理菜单新增「添加观察钱包」入口	2	0.6
导入流程(N-01/N-02)	观察钱包导入页 UI + 6 子态还原	4	1.5
导入流程(N-01/N-02)	地址合法性 / 重复 / 名称校验逻辑	3	1.5
首页只读态(N-04)	首页观察钱包专属视觉 + 提示卡 + banner	4	2
DApp 拦截(N-14)	Provider 层签名前置拦截 + 错误码返回	3	2.4
DApp 拦截(N-14)	签名拦截独立告知页组件	3	1.2
横切	i18n 文案接入（全量 key）	2	0.6
横切	新增 / 必采埋点接入	3	1
测试	QA 测试用例编写（5 类用户 × 全路径）	4	2
测试	跨端联调 + 真机回归	4	3.5
合计			46	19.6
```

> 上表只是格式示例。实际任务、归类与估时**必须**来自你对该 PRD 与该代码库的真实评估。

输出到：`docs/link-ai-prompt/taskSplite/` 下，新建md文档

输出后，简要说明：① 总工时（无AI / 有AI）；② 关键假设；③ Out of Scope 未计入项。需要的话再按「启动前必须确认」第 4 条约定存成 `.tsv` / `.csv` 文件。

## 边界与禁止事项

- **不读代码不估时**：必须先勘察运行目录真实代码，禁止只凭 PRD 字面拍脑袋。
- **不得有 > 4h 的子任务**（以无AI估时为基准），超了就继续拆。
- **不给非目标估时**：PRD 明确 Out of Scope 的不计入。
- **最终交付物用 TSV，不用 markdown 表格**（后者粘进 Excel 不分列）。
- **AI 提效分档给系数，不要全表一个折扣**；联调 / 沟通 / 测试类不要给不切实际的低估。
- **本 skill 只做拆分与估时**，不改 PRD、不写业务代码。
