# progress-work · 项目进度

## 铁律

1. **必须显式调用，而且必须带子命令。** 只有用户亲手输入 `/progress-work <子命令>` 才执行。Claude 不能在对话中自己调用本 skill，也不能因为用户说了"记一下这周的进度""把仓库提交推送一下"就执行——那种情况最多提醒一句可以用 `/progress-work`。frontmatter 里的 `disable-model-invocation: true` 就是为了保证这一点，不要删。
2. **不猜测。** 用户没明确说的、证据里看不出来的内容，不写进文件、不写进提交文案；项目对应不到唯一一个、日期说不准是哪天、参数里有认不出的词，一律先问。
3. **项目以「统计的项目地址」为准。** 那里有几个项目就处理几个，skill 里不写死任何项目名和项目数量。
4. **写之前先让用户看到要写什么。** record 出草稿再写；提交身份必须是 `Aaron <aaron4lawliet@gmail.com>`，不是就停下来让用户确认，不自己改 git 配置。
5. **每次都重新读文件**，不依赖对话里之前读到的内容，用户经常手动改。

## 子命令

| 子命令 | 作用 | 详细流程 |
|---|---|---|
| `record` | 记录进度：单独使用时对所有项目自动整理本周改动；带描述时按描述执行。同时同步项目开发细则 | [record.md](record.md) |
| `draft` | 为每个项目仓库写英文提交文案，只读 | [draft.md](draft.md) |
| `commit` | 提交 | [commit.md](commit.md) |
| `push` | 推送到远端 | [push.md](push.md) |

详细流程只在实际调用对应子命令时读取。`draft` / `commit` / `push` 连用时，按书写顺序读取需要的文件，并先读下文「git 子命令的公共规则」。

### 解析参数

- 子命令必须是 `/progress-work` 后面的第一个词，**大小写敏感、精确匹配**：只认全小写的 `record`、`draft`、`commit`、`push` 这四个词本身。
- **没有参数**：不执行任何操作，回复"需要带子命令"，并列出上面的子命令表。
- **第一个词不是子命令**：不执行任何操作，列出子命令表。包括：
  - 大小写不对：`Record`、`DRAFT`、`Push`；
  - 不是这个词本身：`records`、`drafts`、`record:`、`commit-writer`；
  - 中文或其它说法：`记录`、`提交`、`推送`；
  - 直接写进度：`/progress-work roleflow 写完了 switch`——可以提示改用 `/progress-work record roleflow 写完了 switch`。

  **不要纠正拼写或大小写后执行**，也不要自作主张当成 record 执行。
- `record`：
  - 单独 `record`（后面什么都不写）→ 对「统计的项目地址」里的**所有项目**自动记录本周改动；
  - `record <具体描述>` → **按描述文字执行**。

  两种的细节见 record.md。record 不能和 git 子命令连用。
- `draft` / `commit` / `push`：参数只能由这三个命令词和项目名组成，比如 `draft commit push`、`commit push ai-skills`。后面的命令词同样大小写敏感、精确匹配，`draft Commit`、`draft commits` 里的 `Commit`、`commits` 都算认不出的词。夹了认不出的词（`draft ai-skill`、`commit 一下`）就停下来问，不要猜。

| 输入 | 结果 |
|---|---|
| `/progress-work record` | 所有项目，自动记录本周改动 |
| `/progress-work record 上周的 llmWikis` | 按描述：只看 llmWikis 上周的改动 |
| `/progress-work draft commit push` | 所有项目依次写文案、提交、推送 |
| `/progress-work Record`、`/progress-work records` | 不执行，列出子命令表 |
| `/progress-work push Commit` | `Commit` 认不出 → 停下来问 |

## git 子命令的公共规则（draft / commit / push）

### 范围和顺序

- 没写项目名 → 对「统计的项目地址」里的**每个项目**分别执行，按那一节的顺序。
- 写了项目名 → 只对这些项目执行。
- 每个项目内**按命令书写顺序**执行；重复写的命令词只执行一次。
- 输入命令本身就是授权：`commit`、`push` 不再二次询问"要不要提交 / 推送"。**只有检查结果里「需确认」的情况才停下来问。**

### 第 1 步：检查（任何 git 子命令都先做）

```bash
python3 /Users/aaron/code/ai-skills/skills/progress-work/scripts/git_preflight.py [--project 项目名 ...] [--fetch]
```

命令里有 `push` 时加 `--fetch`，落后提交数才准。脚本只读，对每个项目输出：仓库、分支、上游、推送地址、领先 / 落后、改动数量、提交范围、提交身份、未推送的提交，以及结论：

- **⛔ 阻塞**：不是 git 仓库、detached HEAD、有未完成的 merge / rebase / cherry-pick、没有上游分支（只影响 push）。该项目相应的命令不执行，汇报原因，**不自己去解决**（不 abort rebase、不建上游）。
- **⚠️ 需确认**：
  - **提交身份不是 `Aaron <aaron4lawliet@gmail.com>`**（影响 commit）；
  - **未推送的提交里有作者或提交者不是这个身份**（影响 push）；
  - 将要提交的文件里有疑似密钥 / 凭证，或超过 50MB 的文件；
  - 落后上游，push 可能被拒；
  - 项目地址不是仓库根目录。

**所有项目的「需确认」一次性列给用户，得到答复后再开始执行**，不要执行到一半才问。身份不对时给三个选择：用当前身份继续 / 跳过这个项目 / 用户自己改好 git 配置后重跑。**不要替用户改 `git config`。**

### 提交范围（draft 和 commit 必须一致）

- 暂存区**非空** → 只针对暂存区（用户是有意暂存的，未暂存和未跟踪的不动）；
- 暂存区**为空** → 针对全部改动（已跟踪的修改 + 未跟踪的新文件），commit 时先 `git add -A`。

### 失败处理和汇总

- 某个项目某一步失败：**这个项目**后面的命令停止，其它项目照常执行。
- 全部结束后，每个项目一行汇总本次执行的命令，例如：

  | 项目 | draft | commit | push |
  |---|---|---|---|
  | 项目 A | ✅ | ✅ a1b2c3d | ✅ |
  | 项目 B | ✅ | ✅ d4e5f6a | ❌ 被拒：落后上游 2 个提交 |
  | 项目 C | 无改动 | 跳过 | 没有要推送的提交 |

  只列本次输入的命令；没执行到的写 `—`。
- git 子命令**不会**触发 record，也不改进度文件。
