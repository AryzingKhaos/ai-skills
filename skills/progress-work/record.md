# record · 记录进度

用户输入了 `/progress-work record ...`。record 一次做三件事，**合成一份草稿、一次确认**：

1. 把进度写进「项目记录」表；
2. 按「统计方式」同步「项目开发细则」（宁缺毋滥）；
3. 让表格列和各小节与「统计的项目地址」保持一致。

## 两种调用

### `record`（后面什么都不写）

对「统计的项目地址」里的**所有项目**执行默认流程：自动记录本周一到今天的改动，并同步所有项目的细则。

### `record <具体描述>`

**按描述文字执行。** 先读懂描述要什么，再落到下面的做法；描述里没提到的，沿用默认（范围是本周一到今天，项目是全部，细则照常同步）：

| 描述说的是 | 做法 | 例子 |
|---|---|---|
| 要看的范围（时间、项目） | 只在这个范围内自动记录 | `record 上周`、`record llmWikis`、`record 9 月 1 号到 6 号的 roleflow` |
| 做了什么 | 手动记录：把内容写进对应项目和日期 | `record roleflow 写完 v2 的 switch 子命令` |
| 两者都有 | 两件都做：范围内自动记录，再加上用户说的内容；证据里已经整理出同一件事就不重复写 | `record 本周 ai-skills，另外周三开会定了 roleflow v3 的方向` |
| 对流程的要求 | 照描述调整，没提到的步骤按默认 | `record llmWikis 本周改动，细则这次不用同步` |

- 描述读不懂，或者有两种理解（比如 `record roleflow 文档`，分不清是"看 roleflow 的改动"还是"记一条写了文档"）→ 先问，不猜。
- 日期说不准是哪天（"前几天""最近"）→ 先问。
- 描述里的项目对应不到「统计的项目地址」→ 列出现有项目问用户。

下文的「自动记录」「手动记录」就是这里落下来的两种做法；描述两者都有时，两部分都走。

## 第 1 步：读文件，对齐项目

1. 读全文。项目清单 = 「统计的项目地址」里的全部行。
2. 对照检查，发现的不一致写进草稿的「结构调整」：
   - 地址里有、**当前月份表**没有这一列 → 在表最右边加一列，本月格子留空；
   - 地址里有、「项目开发细则」或「统计方式」没有 `### 项目名` → 加一个空小节；「统计方式」为空的项目本次不同步细则，提醒用户补规则；
   - 表格列或小节里有、地址里没有 → 问用户是否删除。表格列只删当前月份表，而且该列本月有内容时先把内容列出来再问；以前月份的表不动。
3. 项目路径不存在 → 该项目本次跳过，说明原因。

## 第 2 步：整理进度条目

### 手动记录

- **项目**：按 SKILL.md「项目名匹配」确定；一条内容可以同时写多个项目，分别匹配。
- **日期**：没说就是今天；"昨天""前天""9 月 12 号"这类能确定的换算成具体日期；说不准的先问。
- **内容**：只写用户说的事，可以精简措辞，不补细节；同一项目的几件事拆成几条。

### 自动记录

#### 为什么不能只看 git

git 提交只是佐证：提交经常晚于实际修改（攒几天一起提交），没提交的改动看不到，被 `.gitignore` 忽略的目录完全不进 git（比如 llmWikis 的全部 `*Wiki/`）。所以同时看三类证据，互相校验：

| 证据 | 能说明什么 | 盲区 |
|---|---|---|
| AI 会话日志（Claude Code `~/.claude*/projects`、Codex `~/.codex/sessions`） | 哪一刻改了哪个文件、当时在问什么，**日期最准、最能说明"做了什么"** | 用 Bash（sed / cp / 脚本）改的文件不会记成编辑；不用 AI 的手工改动没有记录 |
| 文件修改时间（mtime） | 兜住 Bash、编辑器、Obsidian 里的手工改动 | 同一文件本周改了多次只留最后一次；cp / git checkout / 同步盘会刷新时间；删掉的文件看不到 |
| git | 提交说明帮助理解改了什么；未提交列表；哪些改动被 git 忽略 | 提交可能延迟；只覆盖已跟踪的文件 |

#### 收集证据

不要自己一个个 find / grep，直接跑脚本：

```bash
python3 /Users/aaron/code/ai-skills/skills/progress-work/scripts/collect_changes.py [--start YYYY-MM-DD --end YYYY-MM-DD] [--project 项目名 ...]
```

默认范围是本周一到今天，项目来自「统计的项目地址」，每个项目按「统计方式」里的 `记录排除` 过滤。脚本按「项目 → 日期」输出：

- AI 修改：会话里用 Edit / Write（Claude）或 FileChange（Codex）改过的项目文件；
- 改动会话的提问：上面这些会话当天的提问，最能说明"为什么改"；
- 同目录会话的提问：只是在项目目录下开了会话、没有 Edit / Write 记录的提问——可能是纯讨论 / 查询，也可能是用 Bash 改了文件；
- 文件修改时间：mtime 落在当天的文件；
- git 提交；
- 最后是每个项目的 git 概况：范围结束后才提交的、未提交的、被 git 忽略的。

#### 整理成条目

- **写"做了什么"，不罗列文件。** 一件事一条，同一主题的多个文件合成一条，措辞参考表格里已有记录的风格。
- **读懂再写。** 提问和文件名不够判断时，去看 `git diff` / `git show <hash>` 或直接读文件；还是看不懂的，写"修改了 XX（内容待确认）"并放进「需要你判断」，不要凭文件名编内容。
- **日期归属**：会话日志里的修改时间 > 文件修改时间 > git 作者时间 > git 提交时间。git 提交日期晚于其它证据时，按更早的证据日期记（提交延迟）；只有 git 提交、没有其它证据的，按作者时间记，并标"仅 git"。
- **过滤噪音**：
  - 脚本标了"疑似批量复制或同步"的、只有 mtime 证据的大批文件，放进「需要你判断」；
  - 「同目录会话的提问」要和同一天的 mtime 对照：提问内容和变化的文件对得上（比如讨论某个脚本、当天 mtime 里正好是它），说明是用 Bash 改的，照常写；对不上的（比如在知识库目录里问健身问题、改的是别处的文件）是讨论或查询，默认不写，在「需要你判断」里提一句。
- **查重**：对应格子里已经写过同一件事的跳过，在草稿里标"已存在"。

## 第 3 步：同步项目开发细则（宁缺毋滥）

同步范围：自动记录是本次范围内的项目，手动记录是写到的项目，两者都有时取并集；描述里明确说这次不同步细则的，跳过本步。对每个项目：

1. **按规则核对**：严格按该项目「统计方式」写的路径、对象、行格式、排序、头部摘要执行；规则里给了命令的，**原样运行命令取数**，不估算；一句话概括必须读到源文件（角色文件、SKILL.md、命令文件、index.md 等）再写，不凭记忆或文件名猜。
2. **宁缺毋滥**：
   - 细则只收「统计方式」里定义的**功能点级别的对象**（一个角色、一个 skill、一个命令、一个知识库……）。进度记录里的细节——修 bug、调措辞、补测试、改脚本参数、写了几篇笔记——**不进细则**。
   - **新增一行**的条件：统计对象真实存在而且已经成形（有定义文件、说得清是做什么的）。半成品、空目录、占位、临时 / 备份 / 改名遗留的都不加。**拿不准就不加**，在草稿里写"未加入：原因"。
   - **改写已有一行**的条件：这个功能点的**核心作用变了**。只是细节调整、加了个小选项，保留原措辞，不要每次换一种说法。
   - **删除一行**：统计对象确实不存在了（文件已删除），在草稿里列出来确认。
   - 规模数字（数量、页数、占用空间）按规则如实更新，不算功能点变化。
3. **用户手写的行**（对应不到任何统计对象的）：保留原样，在草稿里提一句；用户确认时说删才删。
4. 头部摘要里的 `同步时间` 只在该项目确实同步过时更新。

## 第 4 步：草稿

按下面的结构展示，没有内容的部分省略：

```markdown
### 进度条目
| 日期 | 项目 | 拟写入 | 依据 |
|---|---|---|---|
| 2026-09-09 周三 | llmWikis | aiagentWiki 新增 LLM 入门材料并转成 podcast 口播稿 | 会话 + mtime（git 忽略） |

### 项目开发细则
- ai-skills：新增 `xxx：……`；skill 33 → 34 个
- llmWikis：investWiki sources 27 → 29；无功能点变化
- roleflow：无变化
- 未加入：skills/tmp-test（没有 SKILL.md）

### 结构调整
- 当前月份表新增一列 xxx

### 需要你判断
- 9/9 aiagentWiki/raw/ 有 21 个文件修改时间相同，疑似批量复制，算不算？

### 证据盲区
- roleflow 本周没有 AI 会话，手工改动只能靠 mtime；有 3 个未提交改动
```

「依据」写证据种类：`会话` / `mtime` / `git` / `未提交` / `仅 git`；手动记录写 `用户`。

## 第 5 步：确认并写入

- **自动记录**：必须等用户确认（全部写入 / 改其中几条 / 取消）。**确认前不写任何东西。**
- **手动记录**：草稿里只有进度条目、细则只有数字和同步时间变化、没有结构调整和需要判断的内容 → 直接写入；否则先确认。

### 写入「项目记录」

- 每个月一个 `### YYYY-MM` 小节，放在 `## 项目记录` 下面，**新的月份放在上面**；月内日期从 1 号到月底升序，每天一行，没有记录的格子留空。
- 日期列格式固定为 `YYYY-MM-DD 周X`，全文唯一，用 `| YYYY-MM-DD 周X |` 定位行。
- **一格里一条进度占一行。** Markdown 表格的一行不能真的换行，多条进度用 `<br>` 分隔；格子已有内容时接在最后：`旧内容<br>新内容`，不覆盖旧内容。
- 格子里不能出现 `|` 和真正的换行：`|` 改写成 `/`。
- 用 Edit 精确替换，不整体重写文件。

要写入的月份还没有表时先建表：

- 列 = 「统计的项目地址」里的项目，顺序一致；
- 行从 1 号到当月最后一天，星期几用脚本算，不要心算：

  ```bash
  python3 -c "import calendar,datetime as d;y,m,n=2026,10,3;print('\n'.join(f'| {d.date(y,m,i).isoformat()} 周{\"一二三四五六日\"[d.date(y,m,i).weekday()]} |'+'  |'*n for i in range(1,calendar.monthrange(y,m)[1]+1)))"
  ```

  `y,m` 换成目标年月，`n` 换成项目数；
- 新表以 `### YYYY-MM` 为标题，插在 `## 项目记录` 下第一个月份小节之前。

### 写入「项目开发细则」

整段替换对应的 `### 项目名` 小节（从标题下一行到下一个 `###` 或 `##` 之前）；只动本次同步成功、且有变化的项目。

### 最后

刷新顶部 `更新时间`。

## 第 6 步：回显

- 进度写了几条、分布在哪几天；
- 细则改了什么（新增 / 删除 / 改写 / 数字）；
- 做了哪些结构调整；
- 跳过了什么、为什么。

## 示例

| 输入 | 处理 |
|---|---|
| `/progress-work record` | 所有项目：收集本周一到今天的证据，同步细则，出草稿，确认后写入 |
| `/progress-work record 上周 llmWikis` | 按描述：只看 llmWikis 上周一到上周日 |
| `/progress-work record 本周 ai-skills，另外周三开会定了 roleflow v3 的方向` | 按描述：ai-skills 本周自动记录，再给周三的 roleflow 手动记一条 |
| `/progress-work record roleflow 文档` | 分不清是看 roleflow 的改动还是记一条"文档" → 先问 |
| `/progress-work record roleflow 写完 v2 的 switch 子命令` | 手动记录：今天 roleflow 格子写入；同步 roleflow 细则 |
| `/progress-work record 昨天 llmWikis 整理了 aiagentWiki 索引；ai-skills 加了 progress-work` | 手动记录：换算成昨天的日期，分别写两个项目 |
| `/progress-work record ai-skills 修了 work-time 的测试，顺便给 rest-check 加了配额查询` | 手动记录：拆成两条 `修复 work-time 测试<br>rest-check 加配额查询`；这些是细节，不进细则 |
| `/progress-work record 前几天 roleflow 改了文档` | "前几天"说不准是哪天 → 先问具体日期 |
| `/progress-work record 学英语 练了 30 分钟` | 对应不到任何项目 → 列出现有项目，问写进哪个，或者提醒先在「统计的项目地址」里加项目 |
