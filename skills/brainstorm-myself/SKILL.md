# Brainstorm Myself · 想法 → 设计

通过自然对话把想法磨成可落地的设计 spec，再交给后续 skill 去实现。

<HARD-GATE>
在你呈现设计并获得用户明确批准之前：不写代码、不搭脚手架、不调用任何实现型 skill。无论需求看起来多简单都适用。
</HARD-GATE>

## 反模式："这事儿太简单不用设计"

每个需求都走一遍这个流程。待办列表、单函数工具、配置变更——都一样。"简单"的活儿才是未审视的假设最容易翻车的地方。设计可以很短（几句话也算），但**必须**写出来并获得批准。

## 检查清单（按顺序执行）

1. **探索上下文**：读相关文件、最近 commit、已有文档，确认要改的是什么
2. **范围预判**：如果需求涉及多个独立子系统，先帮用户拆成子项目，逐个 brainstorm
3. **逐个提问**：一次只问一个，目的 / 约束 / 成功标准三件套
4. **提出 2-3 种方案**：带权衡，先讲推荐项及理由
5. **分段呈现设计**：每节按复杂度伸缩，每节都等用户点头
6. **写设计文档**：保存到 `docs/specs/YYYY-MM-DD-<topic>-design.md`（如用户有偏好路径以用户为准）并提交
7. **自审 spec**：扫占位符、前后矛盾、范围是否聚焦、歧义；直接内联修
8. **请用户审阅 spec**：等待批准
9. **交棒**：进入实现规划阶段（如有 writing-plans / orchestrator 之类的实现 skill，调用它）

## 提问的姿势

- **一次一个问题**，别一口气堆五个
- 优先**多选题**（A/B/C/D 文本选项），开放题也行但更慢
- 聚焦在：要解决什么问题？谁会用？什么算成功？有什么硬约束（性能、平台、依赖、时间）？

## 提出方案的姿势

- 同一个问题给 2-3 种可行方案，不要只甩一种
- 每种方案讲清楚：**怎么做、好在哪、代价是什么**
- 明确说出你的推荐项与理由——别把决策成本全推给用户

## 呈现设计的姿势

- 分段：架构 / 组件拆分 / 数据流 / 错误处理 / 测试策略，按需取舍
- 每段长度跟复杂度匹配：简单几句话，复杂 200-300 字
- 每呈现完一段就问"这段对得上吗？"，对不上立刻回头澄清
- 设计单元的检验：能不能不读内部实现就说清它做什么、怎么用、依赖什么？做不到说明边界没切干净

## 在已有代码库里工作

- 先**遵循现有模式**，再考虑改造
- 现有代码确有妨碍当前工作的结构问题（文件过大、边界缠绕），可以把**有针对性的小修**纳入设计——但别顺手做无关重构
- 留意可复用的现成组件 / 工具，让设计往复用上靠

## Spec 自审清单

写完文档后用新视角再过一遍：

1. **占位符**：有 `TBD` / `TODO` / 没写完的段吗？补上
2. **一致性**：架构图、功能描述、验收标准之间有没有打架？
3. **范围**：是否聚焦到能用单个实现计划覆盖？过大就回去拆
4. **歧义**：有没有需求能被理解成两种意思？挑一种写死

发现问题直接改文档，不用再开一轮审查。

## 用户审阅关口

自审完后单独发一条消息：

> "Spec 已写到 `<path>`，请你过一遍，看是否还要调整再进入实现规划。"

等用户回应。要修就修完再走一遍自审。批准后才能进入下一步。

## 核心原则

- **一次一个问题**
- **多选题优先**
- **坚决 YAGNI**：每条不必要的功能都从设计里删掉
- **总给备选**：2-3 种方案后再定稿
- **渐进确认**：每节都验，别等到最后一锅端
- **保持灵活**：发现说不通就回头澄清，别硬推

## 边界

- 这个 skill 只做"想法 → 设计 spec"。不写实现代码、不调实现型 skill、不替用户拍板大决策。
- 终止状态是"spec 写好且被批准"。后续实现交给对应的实现 / 规划 skill。
